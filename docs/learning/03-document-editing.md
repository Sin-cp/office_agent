# 读取、定位、修改与生成文档

## 操作流程

文件抽屉点击“读取与修改” → 搜索标题或段落 → 选择位置 → 输入替换文字 → 生成新文件 → 下载或继续修改新文件。

本阶段是确定性的文档工具，没有调用大模型；首页提示词草稿仍不发送。

## 三层分工

- `document_service.py`：读取 Word、识别标题层级、判断是否支持编辑、替换指定段落。后续 Agent 可以复用这些工具。
- `documents.py`：HTTP 接口，核对文件、版本、位置和原文，然后保存新文件与来源信息。
- `DocumentEditor.vue`：内容列表、搜索、目标选择、替换文字、结果下载。

`GET /api/files/{id}/content` 返回文档 SHA-256 指纹 revision 和 blocks。块 ID 由文件 ID 与正文段落索引组成，只在该文件版本中有效。空段落也保留索引；表格里的段落不计入本次正文列表。

`POST /api/files/{id}/edits` 接收 block_id、revision、expected_text、new_text。修改前同时核对指纹与原文，防止拿旧数据或其他文件的位置误改。返回新文件对象。

## 为什么不直接重新生成整个 Word

python-docx 用于读取段落和处理目标节点。输出时只替换 ZIP 包里的 word/document.xml，其余条目原样复制内容。未涉及的图片、样式、页眉页脚等包成员保持字节一致。原文件本身始终不变。

整段替换采用首个 run 的格式；段落样式、编号和段落属性保留。新文本不会自动逐字继承原文的混合颜色/加粗。文字长度变化可能改变分页。这不是所见即所得 Word 编辑器。

含超链接、图片、域、书签等复杂节点的段落只读。表格、页眉页脚和文本框不在编辑范围内。标题通过段落或继承样式中的大纲层级识别，手工加粗不自动等于标题。

## 文件关系和数据库迁移

files 表新增可空 source_file_id：上传原文件为 null，新文档指向本次修改的源文件。启动时检测列是否存在，仅对旧表添加列，不删除或重建旧数据。

每次修改创建新的 UUID 文件。用户必须点击“继续修改新文件”才能在修改版上继续操作；保留当前源文件再次修改会产生另一个分支版本。

## 学习重点

1. 文件 ID + 段落 ID 实现准确定位，不使用全局字符串替换。
2. SHA-256 与 expected_text 防止过期数据误写；这是乐观校验。
3. 原始文件不可变，每次操作产出新文件，便于后续撤销和审计。
4. 数据库与文件系统分开，写记录失败要清理本次新文件。
5. 本轮先写稳定工具，后续让模型输出相同接口需要的结构化参数。

部署更新时重新安装后端 requirements 并重启应用，自动添加数据库列；容器部署需要重建后端镜像。更新前备份数据。本次开发不修改线上实例，不推送仓库。
