# 文档处理助手：实现与验收

## 使用方式

项目可以无附件聊天，也可以包含多份源文件。每份文件独立保存当前结果，同名文件不会覆盖；项目之间不共享记忆。选择本轮附件后可以直接输入：

- “总结这份文档，并列出风险”：只显示自然语言回答，不生成文件。
- “提供开头的润色建议”：返回建议，明确要求应用时才生成修改版。
- “删除第二段，在第一段后补充两段说明”：校验整批操作后生成一个版本。
- “将表格第一行第二列改为已完成”：修改对应单元格。
- “继续使用刚才的语气”：参考本项目会话；目标不唯一时追问。

“项目管理”提供标题重命名、继续聊天与源文件列表。纯聊天项目没有文件操作。标题来自首条提示词前 20 个字符，重命名后固定；已有无消息的历史项目暂保留旧名称。文件标签 × 只取消本轮选择，保留会话、草稿与源文件；附件选择按项目在浏览器本地保存。新建对话才退出当前项目。版本恢复已停用，既有生成文件仍可在消息中预览和下载。

## 支持边界

- 正文段落、标题、列表：替换、删除、批量新增，支持标题层级和列表样式。连续在同一位置新增的内容按操作数组顺序排列。
- 常规矩形表格：新增/删除表格，新增/删除行列，替换单元格段落。不能删除最后一行/列；删除整个表格使用删除表格操作。
- 同一批次目标不能包含彼此；除连续新增段落/表格外，目标不能重复。因此同一表格的多次结构变更需分轮执行，表格结构变更也不能与其内部段落修改混在同一批次中。
- 合并单元格和嵌套表格可读取，不能修改。书签范围、域、修订、图片、批注等结构受到保护；对这些结构的修改会明确拒绝，整轮不发布部分结果。
- 未修改的 ZIP 部件保留原字节。正文替换保留未变化文字的 run 格式；新增文字继承受影响位置的格式。新增段落继承锚点段落样式及编号；显式样式必须在文档中存在。
- 阅读覆盖正文和表格，不宣称读取图片文字、页眉页脚、文本框或全部修订内容。不展示专门的阅读范围栏目，但模型收到限制信息，必要时在回答中说明。
- 当前仅支持 DOCX、每份 10 MiB、每轮最多 20 份选中文件、单用户、单进程和一个活动任务。没有增加账号或多人部署权限。

## 接口与数据

`POST /api/tasks` 推荐参数为 `project_id`（首次无附件聊天可省略）、`file_ids`（本轮选择的当前文件 ID 数组，空数组表示不读取附件）、`prompt` 和默认开启的 `web_enabled`。附件必须属于该项目并为当前文件，否则返回 409；普通聊天可以传空数组。旧的单文件参数保留兼容，新前端统一使用项目接口。

结果 `result.kind` 为 `answer`、`clarify` 或 `edit`。前两种展示普通文字；`edit` 的 `outputs` 包含每份生成文件及其 `changes`，单文件时同时保留旧 `file`/`changes` 字段。历史结果的不可用文件不会提供下载。任务轮询及取消接口不变。

| 接口 | 内容 |
| --- | --- |
| `POST /api/projects` | 创建待上传文件的新项目 |
| `GET /api/projects` | 分页项目列表，含 `file_count` |
| `PATCH /api/projects/{id}` | `{name}` 重命名，去除首尾空白后非空，最多 100 字符 |
| `POST /api/files?project_id={id}` | 给已有项目追加一份源文件；多选上传由前端逐份发送，失败文件单独报告 |
| `GET /api/projects/{id}/files` | 源文件及各自的 `current_file`、可用状态 |
| `GET /api/projects/{id}/history?before={task_id}` | 项目任务历史、分页游标、活动任务及源文件 |
| `GET /api/projects/{id}/messages?before={seq}` | 原始消息分页 |
| `POST /api/projects/{id}/restore` | 已停用，返回 410 |
| `DELETE /api/projects/{id}` | 删除项目及全部文件、任务和会话 |

`GET /api/files/{id}/content` 保留旧 `blocks`，新增按正文顺序排列的 `ordered_blocks` 和 `coverage`，避免破坏原单段编辑接口。

SQLite 使用 `conversations`、`messages` 与 `project_sources`，后者独立关联项目、源文件、文件族及当前文件。启动时幂等迁移旧任务；成功、失败和取消状态分别保存。编辑的文件元数据、当前版本、成功任务和回复在同一数据库事务提交；文件保存或事务失败会清理本轮全部输出；发布日志在重启时清理数据库未提交的生成文件。项目删除沿用原来的可恢复暂存机制，并在同一事务删除记忆。

## 上下文和预算

当前版本的原文为事实来源；历史消息只辅助理解用户要求。上下文包括项目摘要、明确偏好、近期对话、覆盖范围和本轮文档。多文件路由先判断是否为聊天、问答、修改或需要澄清；只处理本轮选中的文件。模型身份来自实际 `DEEPSEEK_MODEL` 配置。

历史较长时，通过模型压缩早期消息并保存压缩游标；保留最近四条消息。偏好仅允许从用户明确要求提取。失败和取消的操作不会作为已应用修改。全部完整历史仍保存在数据库。

文档以完整结构块分组，每组约 18,000 字符，最多建立 64 个分块目录。全文处理逐块读取，最多 16 块；局部请求通过分块目录选择最多 8 块，无法可靠定位则追问。全文编辑分块规划后再核对需求完整性，所有操作最终仍基于同一个源版本校验、一次发布。

每轮最多 20 次模型调用（包含记忆压缩），每次 45 秒；模型输出最多 8,192 tokens，单次最多 500 项编辑。完整单块、近期上下文、汇总输入或输出超过预算均明确失败，不静默截断。超大表格或单段暂不拆成可编辑片段，需用户拆分结构后重试。

任务保存 `metrics`（模型名、耗时、状态、token 用量），日志只记录这些元数据，不记录密钥、提示词或文档全文。token 用量来自供应商响应，缺失时为空；没有虚构金额成本。

## 验证

```bash
cd backend
.venv/bin/python -m unittest discover -s tests -v
cd ../frontend
npm run build
npm test
```

测试使用临时数据库和生成的代表性 Word 内容，不调用真实模型。覆盖回答/追问、会话隔离、引用校验、停用恢复与旧版本冲突、批量定位、格式与编号保留、表格行列操作、复杂结构拒绝、取消及事务失败、幂等迁移、长文档分块和记忆压缩，以及纯聊天持久化、多文件独立指针、多文件校验/发布失败整体回滚和重启清理。

真实模型评测（会调用已配置的供应商并消耗用量，仅使用脚本生成的样本文档）：

```bash
cd backend
.venv/bin/python evaluate_assistant.py --live --output /tmp/office-agent-evaluation.json
```

报告记录实际任务类型、文件数量变化、耗时及调用用量。自然语言准确性和版面质量仍需人工检查：用 Word 打开原始文件和生成版本，检查标题、粗体/斜体、列表连续编号、表格边框/列宽、页眉及图片；自动测试通过不等同于 Word 排版验收通过。
