# 全文修改与自动补改

项目任务及旧版单文件任务共用修改流程：明确要求 → 分配章节 → 生成操作 → 临时应用并读取实际结果 → 审核 → 最多两轮补改 → 原子发布。

修改清单区分必需项与可选建议，并引用用户原话。精确里程、时间等用户未要求的建议不作为验收条件；自驾改写保留合理的停车后步行。缺少信息只有在真正阻碍修改时才追问。联网开关及文档联网授权规则不变，关闭联网不妨碍一般改写，未核实事实应标明。

每份文件的原始版本在本轮中固定不变。补改替换受影响分块的完整操作列表，保留其他计划，随后重新应用全部操作。审核读取临时 DOCX 的实际正文与表格；较大结果先分块检查，再统一检查跨章节与跨文件一致性。失败、停止或两轮仍不通过都不发布部分修改。

任务新增可选字段 `activity` 和 `repair_round`（0 为初次生成，1/2 为补改）。前端显示“正在整理修改要求”“正在检查修改完整性”“正在补充遗漏内容（1/2）”。历史记录继续兼容没有新字段的旧任务。内部审核问题不直接作为用户回复；失败提示区分缺少信息、预算不足及补改未完成。

沿用每轮 20 次模型调用、最多 16 个分块、500 项操作、60,000 字符检查输入、10 MiB 文件限制。生成前及每轮补改前预留审核调用；复杂文档可能因调用预算而无法处理全部 16 块，此时明确提示减少附件或缩小范围。修改清单编号或逐字引用不合法时仅允许一次格式纠正，该调用也计入总预算。

验证：

```sh
cd backend
.venv/bin/python -m unittest discover -s tests -q
# 可选真实服务联调，会产生模型用量；使用隔离的模拟西安攻略。
.venv/bin/python evaluate_edit_repair.py --live
```

联调报告默认保存到 `/tmp/office-agent-edit-repair.json`，包括结果文本、生成内容和调用指标，不包含 API Key。无需数据库迁移，更新后重启后端并发布重新构建的前端即可生效。
